## Уточнение владельца 21.10: готовые harness по подпискам

Основной контракт закреплён в `docs/v1-v2-scope.md`, раздел «Owner clarification».
Пять harness — Grok, Claude Code, Codex, Kimi, DeepSeek — получают роли и задачи;
пользователь собирает циклы в no-code. Базовый цикл — пять шагов Рэя Далио, свои циклы
пользователь создаёт и редактирует в Studio. Видны расход, остатки и сброс доступных
подписочных окон (день, неделя, пять часов); неизвестное остаётся неизвестным.
Цель — управлять готовыми harness над их собственными агентными циклами и использовать
уже оплаченные подписки. API не является обязательным способом оплаты этого сценария.

Прежнее ограничение H5-V1 «только API, подписки после V1» отменено этим уточнением.
API-R5 остановлен; ключи не запрашивать. Не объявлять этот основной сценарий выполненным
на основании API-тестов или одних установленных CLI. Остальные проверенные R1–R4 не повторять.

Срез кода 21.10 (не проверка живых аккаунтов): штатные подписочные входы и readers лимитов
есть у Claude, Codex, Grok и Kimi, но выполнение их задач внутри production boundary закрыто.
Общая модель и экран расхода/остатка/сброса уже есть; это снимки квот аккаунта, не доказанная
атрибуция расхода отдельной задаче. Grok reader сейчас понимает неделю/месяц; окна остальных
нужно брать из фактического ответа, не обещать одинаковые пять часов/день/неделю каждому.
Текущий DeepSeek `dsh` допускает только API и читает денежный `/user/balance` — это не подписка
и не её лимиты. Нужны подтверждённые subscription harness и источник квот для DeepSeek;
до этого пункт остаётся открытым, API-балансом его не закрывать.

Ближайшее задание Opus — [H5-SUB-R5](tasks/H5-SUB-R5-TASK.md), подготовлено 21.10:
доделать подписочный запуск и пройти в приложении все пять этапов Далио без API-ключей.
Продолжить вариант B из `tasks/R2-H5-ANALYSIS.md`:
сначала Claude Code 2.1.239 как исполнитель и Codex 0.112.0 как проверяющий на Windows.
Это первый сквозной проход; остальные три harness остаются частью продуктового контракта.
Использовать штатный вход CLI по подписке, измерить минимальный состав временного home
и обновление сессии. Продукт управляет CLI, собственного клиента модельного API не добавлять.

Критерии первого прохода:

- Подтверждён подписочный вход обоих CLI, нет API-fallback и наследования API-credentials.
- Настоящий login-home и исходный проект защищены от записи попыткой; остаётся изоляция.
  `LOGIN_LOAN_OPEN` не включать вместо реализации. Временные credentials не попадают в Git.
- Перенос и обновление credentials учитывают схему, аккаунт, конкуренцию, сбой и очистку;
  настройки, hooks и MCP не записываются обратно из рабочей попытки в личный профиль.
- Plan, preview, authorize, spawn и checker одинаково определяют доступность этого запуска.
- Claude выполняет полезную задачу, Codex проверяет точный результат; исходник меняется
  после явного принятия. Лимиты подписок показываются по свидетельствам, без выдуманных чисел.

Технический остаток H5 нельзя выдавать за отсутствие API-ключей у владельца.
Полный зелёный CI остаётся условием финальной приёмки. Срок реализации подписочного пути
пока не установлен; прежние оценки анализа не являются новым обещанием.

### R0. Проверка восстановленной среды

Выполнено; пункты ниже описывают процедуру восстановления, а не новую очередь
повторных проверок. Полный core suite остаётся отдельной проверкой R5.

1. Записать `git rev-parse HEAD`, `git branch --show-current`, `git remote -v`, `git status --short`; не менять identity Git на выдуманное имя.
2. Использовать Python 3.11+ и отдельную `.venv`. Установить `.[dev,browser]`: даже core suite импортирует Playwright через `tests/test_browser_gate.py`. Chromium нужен для настоящих браузерных проверок.
3. Проверить `conduct --help`, импорт пакета и `conductor.__version__`. У CLI нет `--version`.
4. Запустить демо и проверить, что оно реально обслуживает локальную страницу. Demo не требует входа к провайдерам и использует временную копию данных.
5. Зафиксировать результаты выбранных проверок и что не запускалось. Для полноценного базового прогона core: `python -m pytest -q --basetemp <короткая-временная-папка>`.
6. На Windows использовать короткие пути временных данных. CI специально использует `pt`, `bg`, `bgr`: длинные пути способны вызвать предусмотренный контрактом `windows_path_too_long`. Не «исправлять» продукт, расширяя лимит только ради длинного каталога теста.

## Как сохраняем контекст дальше

Для каждой задачи хранить в Git короткое задание и отчёт: исходный HEAD, ожидаемое поведение, изменённые файлы, реально выполненные команды, результаты, непроверенное, решение ревьюера, следующий шаг. Не включать аккаунтные секреты, raw vendor output и большие CI-архивы в обычные коммиты.

Разделять причины статусов: «реализовано», «локально проверено», «проверено CI», «принято ревью», «принято владельцем». Перед передачей фиксировать `git status`; при параллельных задачах использовать отдельные ветки/worktree или непересекающиеся файлы. Обновлять старый план по итоговому состоянию, а не накапливать противоречивые списки.

После завершённых этапов сохранять проверенные коммиты в согласованном remote. Публикация в GitHub не выполнялась в рамках подготовки этого плана.
