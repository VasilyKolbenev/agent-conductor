- Исполнитель: Claude Code / Sonnet 5.5. Задание Codex от 21.10.2026 по CI № 46, job
  119379019975 (Windows, Python 3.12). Продукт (`src/conductor/boot_kuser.py`) не менялся.
- Исходный commit и ветка: `ff6c250`, `recovery/2026-10-20` (локальные коммиты, не запушены).
- Состояние рабочей копии до изменений: `M docs/recovery/2026-10-20/R5-REHEARSAL-RUNBOOK.md` и
  `M docs/recovery/2026-10-20/tasks/R5-P9-CORE-0a493ad.md`. Это чужие правки, я их не трогал.
- Цель: тест `test_a_read_that_runs_off_the_end_of_the_page_is_reported_as_partial_not_a_crash`
  читал 64 байта от `0x7FFE0FF0` и предполагал, что `0x7FFE1000` недоступна. На runner
  `read_page` вернул байты, и тест упал с `DID NOT RAISE BootRefused`. Нужно: граница, которую
  тест создаёт и проверяет сам, строгий `partial_read`, и отдельная детерминированная проверка
  ветки `0 < got < size`. Retry, skip и увеличение timeout не добавлялись.

## Замеры (до написания теста)

Скрипты и вывод лежат вне репозитория: `C:\Users\Пользователь\Documents\Codex\work\kuser\`
(`measure.py`, `measure2.py`, `stress.py`, `run_mutants.py`, `measure-1.txt`, `measure-2.txt`,
`stress-1.txt`, `mutants-1.txt`). Машина: Windows 11 10.0.26300, Python 3.12.14 AMD64.

- `GetSystemInfo`: страница `0x1000`, гранулярность выделения `0x10000`.
- `VirtualQuery(0x7FFE0000)`: MEM_COMMIT, PAGE_READONLY, MEM_PRIVATE, RegionSize `0x1000`.
  `VirtualQuery(0x7FFE1000)`: MEM_FREE, RegionSize `0x8000`.
- Настоящая KUSER, чтение 64 байт от `0x7FFE0FF0`: `done=False, got=16, error=299`, 100 из 100
  раз; `read_page` отвечает `partial_read`, `only 16 of 64 bytes were read`. Здесь исходное
  предположение теста верно.
- Контрольное чтение 16 байт до границы: `done=True, got=16`.
- Две страницы одним VirtualAlloc, первая READWRITE, вторая в состоянии:
  RESERVED, COMMIT PAGE_NOACCESS, COMMIT PAGE_READWRITE|PAGE_GUARD: во всех трёх
  `done=False, got=0, error=299`, размеры 17, 32, 64, 200, 512, 513 и 4096, по 200 повторов,
  без отклонений. Продукт отвечает `native_unavailable`, `Windows error 299`. Защита
  PAGE_GUARD после чтений осталась (`0x104`). Первая страница READONLY при второй RESERVED и
  при второй NOACCESS даёт то же (`got=0`); вариант READONLY с GUARD не измерялся.
- Обе страницы COMMIT READWRITE (границы нет, как на runner): `done=True, got=64`, 500 из 500;
  `read_page` возвращает 64 байта. Это воспроизводит симптом CI «DID NOT RAISE».
- Одна страница VirtualAlloc, остаток 64 KiB гранулы MEM_FREE (то же для MapViewOfFile и для
  первой страницы READONLY): `done=False, got=16, error=299` при всех семи размерах, по 200
  повторов. Это то же поведение, что у настоящей KUSER.
- Стресс: 3000 циклов «страница, проверка, чтение» при четырёх потоках, выделяющих и освобождающих
  память: 3000 из 3000 `partial_read` с точным detail. Явный `VirtualAlloc` на страницу за
  границей (reserve+commit, commit, reserve) все 9000 раз дал ошибку 487.

Вывод: на этой машине ядро сообщает частичный счёт, когда чтение выходит за конец выделения в
свободное пространство, и сообщает 0, когда недоступная страница лежит внутри того же резерва
(RESERVE, NOACCESS, GUARD). Причина не исследовалась; это наблюдение для сборки 26300, не
документированное поведение.

## Изменения

Только `tests/test_boot_kuser.py` (221 -> 374 строки, самая длинная строка 100 символов).

- Импорты `contextlib`, `ctypes`, `types`; константы `MEM_*`, `PAGE_READWRITE`,
  `ERROR_PARTIAL_COPY`, `FAKE_ADDRESS`, `FAKE_BYTES`.
- `page_before_a_hole()` (контекстный менеджер): размер страницы из `GetSystemInfo`; одна
  страница `VirtualAlloc` (MEM_RESERVE | MEM_COMMIT, PAGE_READWRITE); явные `argtypes` и
  `restype` для 64-битных указателей, как в `tests/node_run.py` и `tests/test_hub_job.py`;
  `PartitionId` в `MEMORY_BASIC_INFORMATION` только при 8-байтовом указателе (winnt.h).
  До выдачи страницы проверяется: гранулярность выделения больше страницы (на этом держится
  «за страницей никто не выделит»); своя страница committed и READWRITE по `VirtualQuery`;
  страница за ней MEM_FREE. Иначе `AssertionError` с названием факта. `VirtualFree` в `finally`.
- Тест с прежним именем: контрольное чтение 16 байт до границы возвращает записанные байты;
  `read_page(address=end - 16, size=64)` даёт `BootRefused` с кодом `partial_read` и detail
  ровно `only 16 of 64 bytes were read`. `@needs_windows`.
- `fake_kernel()` подменяет `ctypes.WinDLL` объектом, чей `ReadProcessMemory` возвращает
  заданные `done`, `got`, последнюю ошибку и пишет первые `got` байт. Четыре теста (10
  проверок): `0 < got < size` (got 1, 16, 63, оба значения `done`) даёт `partial_read` с точным
  detail; `got=0` (оба `done`) даёт `native_unavailable`, `Windows error 299`; `done=False` при
  `got=64` даёт `native_unavailable`, `Windows error 5`; `done=True, got=64` возвращает ровно
  записанные байты. Во всех четырёх тестах проверяется ещё, что фейк спросили про тот же адрес
  и размер (`asked == [(FAKE_ADDRESS, 64)]`): без этого строка могла пройти на настоящем ядре
  (см. «Ревью Opus (две линзы)»). Тесты с фейком идут под своим маркером `needs_fake_kernel`
  (причина пропуска: фейк подменяет `ctypes.WinDLL`, он есть только на Windows).
- Не менялись: тесты разбора, реальные проверки KUSER, `native_unavailable` на `0x10`, тест
  запрета привилегий. `tests/test_command_line_cap.py` не трогал (хэш прежний).

Решения:

- Граница задания (две страницы, вторая RESERVED, NOACCESS или GUARD) измерена и не годится:
  везде `got=0`, то есть `native_unavailable`, а не `partial_read`. Задание велело в этом случае
  остановиться; я не подгонял тест под ответ продукта, а взял другую границу, которую измерил
  (однозначный `got=16`, 3000 из 3000 при нагрузке), и вынес случай `got=0` в вопросы ниже.
- Тесты на фейке идут только на Windows (`needs_fake_kernel`). Безопасность импорта
  `ctypes.wintypes` на Linux/macOS CPython 3.11/3.12 я исполнением не доказал: здесь нет ни
  WSL-дистрибутива (`wsl --list` пуст), ни другого хоста. Косвенно: `conductor.hub.job` и
  `tests/test_hub_job.py` импортируют `wintypes` без охраны, а матрица CI гоняет ubuntu и macos
  на 3.11 и 3.12. Но и этого мало: `ctypes.WinDLL`, `get_last_error` и `set_last_error` есть
  только при `os.name == "nt"` (`Lib/ctypes/__init__.py` этой установки 3.12, строки 475-480), и
  фейку на POSIX пришлось бы подменять ещё и их, то есть тест проверял бы подмену, а не ветку.
  Если Codex хочет эти строки и на Linux/macOS, нужен отдельный проход с прогоном на хосте.
- Строка про `done=False, got=64` не была в задании; она закрепляет, что успех требует и
  `done`, и полный счёт (мутант M6). Если не нужна, строка убирается без последствий.

## Не проверено

- CI runner: почему там соседняя страница `0x7FFE1000` читается, не доказано (карта памяти
  runner не записана). Нативный тест от этого не зависит, но зависит от поведения ядра:
  частичный счёт при выходе за конец выделения в свободную память измерен только на сборке
  26300. Если на runner ядро ответит иначе, тест упадёт на `partial_read`, а не молча пройдёт;
  первый зелёный или красный Windows-прогон CI это покажет. Что известно из CI и что
  правдоподобно, но не доказано, см. «Ревью Opus (две линзы)», находка 2.

  здесь только 3.12.14 (`py`-лаунчера и другого интерпретатора нет). Используемые API
  (`byref(...)._obj`, `ctypes.set_last_error`, `VirtualQuery` через ctypes) в 3.11 есть;
  подтвердит первый CI.
- Полный suite не гонялся (по рамке задания), Linux и macOS не гонялись вовсе.
- 32-битный Python: ветка без `PartitionId` в `MEMORY_BASIC_INFORMATION` не исполнялась,
  доступен только 64-битный.
- `tests/test_boot_kuser.py` не внесён в `CAPPED`: список ведёт ведущий; лимит строк файл
