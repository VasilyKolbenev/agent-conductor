- Исполнитель: Claude Code / Sonnet 5.5.
- Исходный commit и ветка: `4d0e3af` (`style(desk): the motion bench ends with one newline`), ветка
  `feature/v1-desk-integration`. К концу работы HEAD сместился на `6a6d693`: два docs-коммита
  восстановления (`8117fe5`, `6a6d693`) поверх `4d0e3af`; `git diff 4d0e3af 6a6d693 -- src tests`
  пуст, продуктовый код и тесты они не меняли.
- Состояние рабочей копии до изменений: незакоммиченные `AGENTS.md`, `CLAUDE.md`,

  Изменений отслеживаемых файлов продукта не было.
- Цель и наблюдаемое ожидаемое поведение: confined adapter, которому платформа `"win32"` передана
  явно (`adapter.confine("win32")`), на POSIX доходит до `ProcessRunner.container_profile` и
  получает штатный отказ раннера `CommandSpecError`, а транспорт адаптера превращает его в
  фиксированную `adapter.error`. Сейчас вместо этого наружу уходит `ImportError: Windows process
  creation is unavailable on this platform` из `_winlaunch.py:17`.

## Дефект

CI run 39149580847, все четыре POSIX unit-job:
`tests/test_adapter_boundary_launch.py::test_a_confined_adapter_over_the_shipped_runner_starts_no_task_child`.

Цепочка: `adapter.confine("win32")` → `harness_attempt._hold_boundary` пропускает (платформа задана явно,
намеренно) → `_spawn` → `_run_confined` → `ProcessRunner.container_profile` →
`from . import _winlaunch` → модульный guard `_winlaunch.py:16-17` бросает `ImportError`.
`LAUNCH_REFUSALS = (ProcessRunnerError, OSError, OwnerRefused, ProfileRefused)` его не ловит.
У соседнего `ProcessRunner._launch` проверка `os.name != "nt"` стоит ДО импорта `_winlaunch`;
у `container_profile` её не было.

## Изменения

- `src/conductor/command/adapters/process.py` (+7/-1):
  - новая модульная константа `_NO_WINDOWS_BOUNDARY = "Windows boundary is unavailable on this
    platform"` рядом с `_VIEWING` (то же предложение, что раньше стояло литералом в `_launch`);
  - `ProcessRunner.container_profile`: сразу после отказа `_spawns_allowed` и до
    `from . import _winlaunch` (и до `_loaned`) — `if os.name != "nt": raise
    CommandSpecError(_NO_WINDOWS_BOUNDARY)`; порядок проверок прежний (сначала просмотр, затем
    платформа, затем импорт и `_loaned`);
  - docstring `container_profile` дополнен фразой: вне Windows раннер отказывает
    (`CommandSpecError`) до импорта нативного помощника, ничего не создавая;
  - `ProcessRunner._launch` теперь использует ту же константу (текст отказа не изменился).
- `tests/test_execution_boundary.py` (+9): новый свидетельский тест
  `test_the_runner_entry_agrees_with_the_predicate_on_the_platform_the_test_runs_on` рядом с
  `test_the_predicate_agrees_with_the_runner_on_the_platform_the_test_runs_on`. Если
  `boundary_provided(sys.platform, "dispatch")` — возвращается (Windows-путь покрыт в других тестах).
  Иначе: `ProcessRunner(tmp_path).container_profile(mode="dispatch")` бросает `CommandSpecError`
  с match `unavailable on this platform`; `tmp_path` пуст (`list(tmp_path.iterdir()) == []`);
  `_winlaunch` не импортирован.
- Не менялись: `_winlaunch.py`, `LAUNCH_REFUSALS`, существующий тест
  `test_a_confined_adapter_over_the_shipped_runner_starts_no_task_child` (без skip/xfail/правок),
  `recover_container_profiles`. Размеры (физические строки, как считают проверки лимита
  `len(source.splitlines())`): `process.py` 781 из 800 — запас 19 строк;
  `test_execution_boundary.py` 120. Исходная цифра «696/77» была числом непустых строк
  (`Measure-Object -Line`) и исправлена при ревью.

Отличие от задания: последняя проверка в новом тесте написана как
`sys.modules.get("conductor.command.adapters._winlaunch") is None`, а не `... not in sys.modules`.
На настоящем POSIX поведение то же (проваленный импорт не оставляет запись в `sys.modules`).
Разница в имитации: плагин `posix_sim` кладёт `None` под этот ключ, и `not in` падал бы там
независимо от правки.

### Известный неохваченный путь

`ProcessRunner.recover_container_profiles` (process.py:~503) по-прежнему делает
`from . import _winlaunch` без платформенной проверки. В `src` у него нет вызовов (grep по
`recover_container_profiles` находит только определение), поэтому на CI он не сработал; при
появлении вызова на POSIX он даст тот же `ImportError`. Вне объёма R1.1, не менялся.

## Ревью Opus и правки после него

Независимое ревью Opus 5.5 — workflow `r1-1-review`, четыре ракурса: контракт, регрессии
на POSIX, сохранение Windows-защиты, качество проверок. Каждую находку выше уровня note

1. `assert sys.modules.get("...._winlaunch") is None` пуста. На POSIX проваленный импорт

   она не доказывала.
