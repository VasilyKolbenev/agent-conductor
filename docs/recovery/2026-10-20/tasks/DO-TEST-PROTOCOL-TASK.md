# DO-TEST-PROTOCOL: тесты до checker и материалы отказа

Решение владельца 11.11.2026. Без vendor/model calls и нового живого цикла;
порог 30% остатка. Исходная база `3a113c2`, существующий run не повторять.
Рабочий стандарт обязателен; исправление не означает готовый выпуск или установку.

Подтверждённый сбой: counter-src-4deb571-r2, Do verification_failed из-за отсутствия
протокола тестов. Внешние 4 passed получены после checker и не изменяют его verdict.
Inspector скрывает diff/checker/findings отказа, хотя журнал содержит CorrectionFeedback.

## Порядок срезов

1. Сначала воспроизведение на публичной дороге, красное на отсутствии реального
   протокола перед checker; существующие protections и assertions не ослаблять.
2. После применения патча запускать объявленные тесты, затем независимый checker.
   Runner — проверенный инструмент проекта, не команда модели и не shell.
   Offline boundary, без credentials, read-only дерево, собственный scratch;
   timeout входит в Do deadline/бюджет, output конечен, stderr не терять.
3. Сохранить argv, cwd, status/exit, stdout/stderr и итог с привязкой
   run/action/attempt/tree/snapshot/test policy. Checker получает этот протокол
   и те же байты файлов. Пропуск, ноль тестов, ошибка и timeout не означают passed.
4. Связать отклонённую попытку с её неизменяемым снимком; не брать latest/live tree.
   Inspector показывает diff, протокол, checker и findings с отрицательным статусом.
   Это не делает снимок принятым и не открывает финальную приёмку.
5. Локальные двойники: порядок apply → tests → checker, failure/timeout/truncation,
   binding mismatch, чужая попытка, сохранность original, no-op mutant.
   UTF-8 и native Windows, отдельно source и browser checks. Новых моделей нет.

Перед реализацией нужны DESIGN и две независимые линзы; существующий внешний
import_test_evidence хранит только counters и не считается executor или протоколом.
Не hardcode test_counts.py или unittest как универсальный контракт всех проектов.
Установка runner/dependencies, host fallback и расширение полномочий не входят в scope.
Отсутствующий доверенный toolchain — явный отказ, а не исполнение на host.

## Уточнение автономности владельца

Будущие циклы продолжают исправление после REJECT: замечания checker возвращаются
участникам, те устраняют причины и снова предъявляют результат по критериям цели.
Это не слепой повтор той же попытки и не обязательный перезапуск Goal с нуля.
Работа продолжается в согласованных границах, при наличии бюджета и доступа;
при исчерпании — сохранение прогресса и пауза с возможностью продления разрешения.
UNKNOWN, потеря доступа, смена scope и требуемое решение владельца не обходятся циклом.
Прежние no-retry grants не меняются задним числом. Полноценные петли и адаптивные
бюджеты — отдельный срез после доказанного test/checker пути.
