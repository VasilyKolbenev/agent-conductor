### Три отступления от текста задания

1. **Не `report.capstderr`, а секция собственной фазы отчёта.** Задание говорит просматривать
   `report.capstderr`. Но pytest хранит захваченные секции всех фаз на самом тесте и кладёт их на
   каждый следующий отчёт: `capstderr` отчёта teardown содержит заново строки setup и call. Первая
   версия по заданию считала одну строку до трёх раз; это показал тест с настоящим дочерним pytest
   (`test_the_real_hooks_...` получил лишние записи фаз `call` и `teardown` у тестов, чья строка
   пришла в другой фазе). Читается только секция `Captured stderr <когда>` самого отчёта. Мутант M4
   (вернуть `capstderr`) краснит два теста.
2. **Поле `kind`.** Три вида записей лежат в одном файле, как говорит задание, поэтому нужен
   различитель. Поля, названные заданием, сохранены.
3. **Итоговая строка пишется для каждого модуля, даже молчавшего.** Иначе «событий нет» нельзя
   отличить от «счётчик не работал». Модуль регистрируется по первому же отчёту.

### F1: «счётчик не меняет код выхода и вердикт» теперь держат тесты

- Дочерняя сессия pytest (`INNER`, копия conftest) запускается дважды на одном проекте: без
  переменной gate и с ней. Код выхода, список упавших узлов и итоговые числа (без времени) должны
  совпасть, а вооружённая сессия обязана действительно услышать (файл `netfail` — число строк);
  без переменной ничего не пишется. Три тела: все виды строк и все тесты зелёные
  (`6 passed`, код 0, 5 событий); то же с одним падающим тестом (`1 failed, 5 passed`, код 1);
  ничего не слышно (`1 passed`, код 0). В `INNER` добавлен тест, который через обёртку conftest
  стреляет `requestfailed` с `ERR_NO_BUFFER_SPACE`, чтобы сессия слышала оба вида событий.
- Настоящий `gate.run_gate` (keep-going) над модулями теста с копией настоящего conftest, в обоих
  порядках: модуль с услышанной строкой 10055 и тихий дают `green`, `complete`, коды 0 и 0,
  `pytest_end = ordinary`, ноль waiver'ов; у громкого модуля в `netfail` запись `passed`.
  Отдельный прогон из четырёх модулей (громкий и тихий, зелёный и красный каждый): красными
  остаются ровно два красных, громкий зелёный не краснеет, у громкого красного те же код,
  `pytest_end` и счётчики waiver'ов, что у тихого красного, запись `outcome = failed`.
- Мутанты на копиях (`work\r13e1f\mut\`, скрипт `mutate.py`): F1a `session.exitstatus = 1` в
  любой вооружённой сессии — 11 красных; F1b то же при услышанной строке Chromium — 4 красных;
  F1c при услышанном `requestfailed` — 1 красный (только дочерняя сессия); F1d услышанная строка
  «моет» красную сессию в зелёную — 4 красных; F1e услышанная строка делает отчёт `failed` — 14
  красных. Красные при F1b — только новые тесты (три функции с параметрами), прежние 34 случая при
  нём проходили, как и сказано в ревью.

### F2: один инцидент не считается дважды

Выбрано «отдельные поля без суммы». Поле `events` (`chromium_lines + requestfailed`) убрано;
итоговая строка несёт два счётчика. Причина: правило решения раздела 8 («≥ 5 на порядок») считает
инциденты, а один отказ connect даёт и строку Chromium, и `requestfailed`, так что сумма
удваивала бы его. Дедупликация по тесту и времени не выбрана: время строки Chromium и время
доставки `requestfailed` не совпадают (отставание на длину вызова Playwright), значит окно
сопоставления было бы подбором. Для правила берётся `chromium_lines`: каждая его запись несёт
исход теста, значит «в прошедших тестах» читается прямо; `requestfailed` остаётся для часов и
как независимая проверка. Gate ставит `DEBUG=pw:browser*` всегда, поэтому строки Chromium слышны;
без него (локальный запуск) остаётся один `requestfailed`. Отступление от пункта 3 задания («число
событий за модуль»): вместо одного числа два.
Тест: один инцидент, услышанный обоими путями, даёт `chromium_lines = 1`, `requestfailed = 1`,
набор ключей итоговой строки равен ожидаемому, и **ни одно значение не равно 2**, то есть нет суммы
ни под каким именем. Мутанты F2a (`events` вернулся) и F2b (`incidents` — сумма) красные (по 1).

### F3: файл `netfail` заменяется при первом открытии в сессии

`_netfail_write` открывает файл на `w` в первый раз за процесс (множество `_NETFAIL_OPENED`, ключ —
полный путь), дальше на `a`; как другие пофайловые артефакты gate, которые новый запуск заменяет.
Процесс здесь и есть сессия (gate запускает процесс на модуль), как и у остальных счётчиков
модуля. Тесты: устаревший файл заменяется первой строкой, файл другого модуля не тронут; строки
одной сессии после первой дописываются (три строки и итог); молчавший модуль заменяет старый файл
