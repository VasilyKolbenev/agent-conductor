## P2: новый тест CPU требует ресурса, которого планировщик не гарантирует

Файл `tests/test_node_run.py`, строки 250–257, особенно 254.
`timed_out()` по умолчанию даёт процессу одну секунду обычного времени; тест требует
не менее 0.5 секунды пользовательского CPU для `while (true) {}`. Запуск Node и ожидание
процессора входят в обычное время, но не дают процессу CPU. Правильная диагностика тогда
делает тест красным на загруженном или медленно стартующем runner.

Воспроизведение без изменения исходников: affinity только собственного тестового Python
и его детей ограничена одним разрешённым процессором; три конкурирующих Node-процесса
самоограничены шестью секундами. Тот же тест упал с **`0.031 >= 0.5`**. Без конкуренции
он прошёл в основном наборе. Все дети завершены, affinity восстановлена.
Эксперимент выполнен один раз; он доказывает чувствительность к нагрузке, а не её частоту
на GitHub и не причину исходного CI #43. Отдельный скептический разбор находку подтвердил.

Исправление для следующего коммита:

- Детерминированно проверить перевод Windows FILETIME из 100-нс единиц, порядок
  user/kernel и форматирование на заданных значениях.
- Сохранить проверку настоящего процесса, читаемости профиля и структуры результата
  без минимальной доли CPU за фиксированное обычное время.
- Пересмотреть и пороги `working set >= 10 MB`, `handles >= 30` на строке 256:
  это также свойства конкретной версии Node и среды, а не контракт диагностического кода.
- Не повышать рабочий timeout и не добавлять retry ради устранения этого ложного падения.

## Остальные ревью и технические решения Codex

### R4

R4-V1 `333dffd` корректен в границах сохранённого состояния одной вкладки: проверка
использует signer данного шага, обычное действие — текущего человека. Смена человека
перед новым действием возвращает подтверждение. Серверной памяти исходного signer нет.
Другая вкладка/новое полное действие могут создать запись с другим actor; прежняя вкладка
push получает `acceptance_exists`, а PR может вернуть стоящую запись. Спецификация это
ограничение теперь отражает. Не называть исправление серверной гарантией авторства.

Технические решения по ранее открытым вопросам:

- **В3 / D1:** вариант A утверждён. Второй look определяет результат даже после ошибки
  входа от push; ошибка чтения не превращается в успех. Не более одного push за запрос.
- **В2:** уточнить обещание терминальной команды: совпадает argv, но приложение отключает
  hooks и интерактивный вход (`tool_env.py:43–47`). Идентичное окружение не обещать.
- **В4 / O3:** сохранить принимаемые адреса; описать optional завершающий `/` в spec 9.7.
- **R4-G:** добавить `tests/test_desk_accept_publish.py` в CAPPED (756 строк,
  максимум 100 символов). Разделение сейчас не нужно; signer уже в CAPPED.
- **В4 / O2:** прежний UX-пробел остаётся. Независимый Node-probe подтвердил:
  после `store_error` показываются условия заново, после `git_failed` — «Отправить снова»,
  хотя внешний эффект мог произойти. Сервер читает remote перед повторным push, поэтому
  само по себе это не доказательство дубликата. Решение Codex: после send/check неоднозначный
  результат трактовать как unknown и предлагать проверку; закрепить G8. Требуется отдельная
  ограниченная правка с тестом. Не записывать этот пункт как закрытый R4-V1.
