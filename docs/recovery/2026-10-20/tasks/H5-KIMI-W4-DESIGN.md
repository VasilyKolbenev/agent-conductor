# W4. Проверка DACL исходных credential при выдаче прав на relay

В `process_loans.py:211` уже загружен проверенный ProviderConfig с protocol и auth_home.
На строке 227 наружу передаётся только realpath. Имя каталога выбирает пользователь
(`provider_setup.py:352`), оно может быть одинаковым для разных протоколов в разных проектах.
`relay_home.py:384` проверяет лишь верхний уровень. Ни один из этих фактов сам по себе
не доказывает, что контейнер открыл вложенный файл. Это устанавливает нативный опыт ниже.

1.1. Предпочтительный вариант сохраняет protocol вместе с исходным написанием auth_home из
одного снимка ProviderConfig до проверки всех соседей при фактической выдаче прав. Проверка
пересечения путей по-прежнему получает канонический путь. Для одинаковых директорий берётся
объединение требований, независимо от порядка строк. Readiness Kimi передаёт собственный
протокол. Выдача relay любого провайдера проверяет каждый настроенный Kimi в своей границе.
На подмену протокола или непроверенное имя нельзя отвечать успешной проверкой как плоского
профиля. Форма конфигурации оператора и байты утверждённых grant не меняются.

1.2. Проверять два code-owned имени `kimi-code.json` и `kimi-code-env-0e4f99c69cc27850.json`
под фиксированным `credentials`, независимо от выбранного региона. Не открывать TOML или
содержимое файлов. Проверять отсутствие или DACL каждого по компонентам с удержанием
проверенных каталогов, без перехода через reparse. Только доказанное отсутствие компонента
считается отсутствием. Ошибка доступа, ссылка, неверный тип или неоднозначность дают отказ.
Вариант поиска такой структуры во всех каталогах без protocol меняет область проверки чужих
профилей. Определение по имени каталога пропускает произвольные законные имена.

1.3. Текущая проверка снимает hold сразу после снимка (`relay_home.py:322`). Проверить один раз
и закрыть handle недостаточно для гарантии при подмене до запуска. Новый договор должен
определить срок удержания имён, порядок доступа с login/rotation и границу угроз. Даже
удерживаемый файловый handle не исключает изменения WRITE_DAC владельцем или появления
ранее отсутствующего файла. Для обещания защиты от конкурирующего владельца нужно отдельное
решение о границе доверия и механизме на весь срок процесса. Не выдавать такое обещание
на основании проверки статического снимка.

1.4. Свидетель RED записывает два настоящих project ProviderConfig с произвольными именами
логинов, создаёт фиктивный файл с собственной ACE и пытается открыть его для чтения из
контролируемого PowerShell AppContainer через relay Claude. Байт не читается. Контроль
положения — без ACE открытие отвергнуто именно ERROR_ACCESS_DENIED. После опыта проверяются
identity, DACL и размер. Исправление должно отказать до появления профиля и записи о займе.
Отдельные проверки нужны для второй географии, разрешённого случая, junction, ломаного
пути, конкурентной rotation, неизменности плоских профилей и уровня readiness.

Стоп перед runtime: требуется отдельное решение об интерфейсе и сроке действия гарантии
(1.1, 1.3). Поведение чужих настроенных профилей и выдача прав меняются; K2 остаётся закрыт.
