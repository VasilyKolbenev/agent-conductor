Итог: локально проверено на Windows. TASK/DESIGN f3f1bc0, реализация a15564c, отдельная ветка codex/kimi-k2a-stage от 3dbbc48. Изменён только инженерный CLI и его тесты. Продукт не получил новое право запуска.

- Дочерний процесс создал закрытую папку, config.toml и credentials/kimi-code.json относительно исходных Windows handles. В отдельной opt-in репетиции один процесс держал дерево, второй пытался переименовать каждый объект. Все четыре операции получили отказ до явного release. Журнал хранит identity и последовательность durable записей, в нём нет байтов фиктивного входа. Только после проверки всего оставшегося дерева начинается удаление по handle.
- Прерванный процесс восстанавливается новым процессом. У записанного частичного stage есть безопасный retire. Объект из промежутка «создан, ещё не записан» пуст и не удаляется. Подмена обычного файла, hardlink, junction, лишний или недостающий объект, оборванная запись дали отказ до удаления даже обычного соседнего config. Приманка снаружи сохранилась. Повтор успешного recover идемпотентен.
- Проверка конкурирующего держателя отдельно воспроизвела ложное завершение: Windows может сохранить уже delete-pending каталог, пока жив внешний читатель (1 failed). Теперь журнал получает retired только после фактического исчезновения каталога. Освобождение внешнего читателя и повторный recover завершают уборку (1 passed).

Для повторения в окружении проекта: `python scripts/kimi_stage_probe.py run <32 строчные hex-цифры>`. Уникальный ID создаёт отдельный каталог в TEMP; после успеха в relay остаётся только несекретная опись. Другой ID с режимами interrupt и recover воспроизводит остановку и восстановление. CLI принимает только закрытый сценарий и ID, не принимает путь к входу или команду.
