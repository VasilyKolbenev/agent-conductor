он назначает им роли, запускает стандартный цикл Далио и получает полезное изменение,

Этот первый проход: Windows, Claude Code **2.1.239**, Codex **0.112.0**, готовый `dalio-v5`.
Пять harness и пользовательские no-code циклы остаются контрактом V1; Grok, Kimi и DeepSeek
подключаются следующими заданиями. Здесь не строить новый движок, редактор или API-клиент.
Сохранить редактирование своих циклов и существующие рабочие сценарии.

Приоритет — работающий проход, а не новый круг исследований. Историческое решение H5-V1
«подписки после V1» отменено владельцем; действующий контракт — `docs/v1-v2-scope.md`,
раздел Owner clarification от 21.10. Реализацию, обычные проверки и подготовку интерфейса

## 1. Довести подписочный запуск

Использовать отдельные login-home продукта и штатный интерактивный вход владельца:
Claude `auth login --claudeai` с `CLAUDE_CONFIG_DIR`; Codex `login` с `CODEX_HOME`.
Не забирать глобальный профиль рабочего Claude/Codex и не просить токены в чат.
Подтвердить именно подписочный метод и план: exit 0 сам по себе недостаточен.
Для Codex ожидается подписочный статус `Logged in using ChatGPT`; API-статус не принимать.
Никакого автоматического переключения на API-биллинг или запуска без изоляции при ошибке.

Довести вариант B для двух pinned CLI, переиспользуя существующие lease и process boundary:

1. До запуска копировать только объявленные credentials и минимальный проверенный bootstrap.
   Подтвердить состав на этих версиях: Claude `.claude.json` может содержать MCP-настройки,
   Codex `config.toml` — исполняемую конфигурацию. Целиком home не копировать.
   Для Codex явно проверить поддерживаемое файловое хранилище; не считать keyring файлом.
2. Временный home с credentials размещать в приватном runtime вне исходника, рабочих копий,
   Git и синхронизируемых папок. Проверять реальный путь, тип файлов, размер, ссылки и reparse.
   Личному login-home не выдавать права дочернего AppContainer; `LOGIN_LOAN_OPEN` оставить закрытым.
3. Запускать CLI через существующий адаптер. Поддержать и planning/review Claude, и dispatch,
   и независимую проверку Codex: одного успешного `do` недостаточно для пяти этапов.
4. Под lease возвращать только допустимые credential-файлы: проверка схемы, неизменных полей
   и аккаунта, CAS против исходного состояния, атомарная замена. Настройки, hooks, MCP,
   журналы и другие файлы из попытки не переносить обратно в login-home.
5. При конфликте, неполном файле, сбое, отмене или неизвестном результате refresh не затирать
   личный вход. Завершать и очищать временные данные безопасно; использовать штатное recovery.
   Если нужен повторный вход, сказать об этом. Ошибка возврата credentials после работы CLI
   не должна превращать выполненную попытку в сообщение «ничего не запускалось».
6. Plan, preview, authorize, transport/spawn и checker должны использовать одно решение
   о поддержке пути. Неготовые профили по-прежнему отказывают до claim; готовые допускаются
   только при выполнении необходимых условий. Удалить устаревшее объяснение про API-only V1.

Секреты не выводить в команды, логи, отчёты, артефакты и Git; учитывать обе копии при redaction.
Модели брать из согласованной конфигурации, фиксировать доступную идентичность в доказательствах;
не подменять выбранную модель или аккаунт незаметно ради успешного прогона.

## 3. Пройти первый цикл в настоящем December Command

Использовать небольшой пакет `runstats` и готовый brief из runbook, не сам репозиторий продукта.
Планируемый корень — `C:\Users\Пользователь\DecemberRehearsal`; сначала проверить, свободен ли он.
Не перезаписывать существующий проект. Начальный дефект `count_succeeded(rows)` — `return len(rows)`.
Результат: считать только словари с точным `outcome == "succeeded"`, не менять вход,
обработать пустой список и другие исходы; стандартные `unittest`, без сторонних зависимостей.
Область изменения: `runstats/__init__.py`, `runstats/counts.py`, `tests/test_counts.py`.

В приложении опубликовать workflow из `dalio-v5`, создать задачу и назначить роли:

| Роль | Harness |
| --- | --- |
| `role-thinker` — goal и identify | Claude Code по подписке |
| `role-diagnostician` — diagnose | Claude Code по подписке |
| `role-designer` — design | Claude Code по подписке |
| `role-implementer` — do | Claude Code по подписке |
| `role-checker` — независимая проверка do | Codex по подписке ChatGPT |

Пройти **goal → identify → diagnose → design → решение владельца → do + checker →
решение владельца о результате**. Первые четыре этапа должны оставить связанные артефакты;
это не демонстрация одного `do`. Показать опубликованную ревизию, роли, план и Policy в UI.
Human gates не нажимать от имени владельца. Обычные разрешённые шаги не требуют нового
подтверждения в чате; на gates подготовить понятный результат для решения владельца.

Codex проверяет точные байты результата Claude: сохранить связь с digest и потреблёнными
материалами. Проверка должна иметь реальный verdict, а не только exit 0 или текст исполнителя.
При reject разрешена одна коррекция do в пределах бюджета; второй reject останавливает проход.
Исходник не меняется до явного принятия владельцем. Проверить diff и `unittest` рабочей копии.
После принятия применить результат предусмотренным runbook способом и проверить исходник.

Сохранить запуск, обновить страницу и перезапустить сервер штатно через Ctrl+C после начала
обслуживания. Артефакты, решения и проверка должны восстановиться без повторного вызова harness.
До и после показать квоты обоих аккаунтов: доступные окна, расход/остаток, время сброса,
источник и свежесть. Недоступное обозначать неизвестным; дельта аккаунта не доказывает расход
именно этой задачи. Не создавать одинаковые окна или значения для разных вендоров.

## Бюджет и завершение

Один основной запуск: обычно **5 task actions + 1 checker**; с одной коррекцией —
**не больше 6 task actions + 2 checker**, то есть до 8 запусков harness для задач и проверки.
Это не ограничение внутренних LLM-запросов или tool calls: ими управляют сами harness.
Login/status/quota учитываются отдельно. Если необходим живой технический probe до цикла,
ограничить его одним минимальным запуском каждого CLI и записать отдельно; не гонять
аккаунты серией скрытых экспериментов. Дополнительный цикл автоматически не начинать.

Отрицательные сценарии checker проверить целевыми тестами. Если в живом цикле не было reject,
так и написать: отдельный живой negative control из старого runbook этим заданием не доказан.
Первый цикл не равен всей R5-приёмке или завершению V1; оставшиеся условия сохраняются в плане.
