## Проверенный вариант для следующего шага

Настоящий codex exec в режиме только чтения сохранил ответ локального двойника в файл
через обычный выход CLI. Патч объёмом 315 байт имеет SHA-256
`dceffd06262e968fb72d0da88fc5b3c95c5965a7a56d9f17ba1b4409efaf9ba9`.
Отдельный запуск патчера в AppContainer принял только этот известный учебный ответ.
Для целевого файла хеш изменился с
`79fd0a46778eaa2ce0f2308a05052204be4c85e8760043fcbe08fd7de09cf6b1` на
`7e4a531a87d32a094e47716085ed597e1e22fc5469d5ed1e583126783f5b7fa8`.

Два процесса проверены на отдельных стендах. В продукте такой маршрут пока
не реализован. В старом живом запуске не сохранился протокол инструментов;
сегодняшние опыты не устанавливают, какой инструмент тогда выбрала модель.
Независимый Codex checker в этих опытах не вызывался, итоговое решение не записывалось.

Следующий технический срез — испытать режим «предложить патч → проверить границы →
применить → независимая проверка» на обычном входе Do. Оба действия должны быть
видны до разрешения. Проверять пути, ссылки, лимит размера, ожидаемые исходные
байты и итоговый diff. Потерянный ответ не должен повторно применить патч.
Ошибка в середине патча должна оставлять доказуемое состояние. До выбора этого
маршрута для продукта требуется решение по дизайну; внутренний ключ патчера
закреплённой версии сам по себе не является обещанием поддержки у вендора.
Полный Далио остаётся на verification_failed.
