## 1. Механизм `subprocess.run` на Windows и что из него следует

Номера строк `subprocess.py` в трассировке CI (550, 1209, 1630) совпадают с локальным 3.12.14.

- `run()`, стр. 548–564: `with Popen(...)`, затем `communicate(input, timeout=30)`. При
  `TimeoutExpired`: `kill()`, на Windows ещё раз `communicate()` **без таймаута**, чтобы собрать
  вывод в `exc.stdout` и `exc.stderr`, и `raise`. Выход из `with` закрывает pipe и ждёт процесс.
- `communicate()`, стр. 1203–1209: `endtime = time.monotonic() + timeout`.
- `_communicate()` для Windows, стр. 1603–1634: два потока-читателя (`fh.read()` до EOF), затем
  в основном потоке и **без таймаута** `_stdin_write(input)` (запись и закрытие stdin), затем
  `stdout_thread.join(остаток)`; если поток жив, `raise TimeoutExpired` — стр. 1630, как в CI.
- `kill()` = `terminate()`, стр. 1667–1680: `TerminateProcess(handle, 1)`. Если процесс уже
  завершился, вызов отказывает, и `returncode` берётся из `GetExitCodeProcess` — это
  собственный код процесса.

Что из этого следует для CI №43.

- Исключение поднято на стр. 1630. Значит, `_stdin_write` вернулся: 607 символов записаны и
  stdin закрыт. Поток чтения stdout не получил EOF за 30 с.
- `<Popen: returncode: 1 ...>` в трассировке. pytest форматирует repr после того, как
  `except`-ветка `run()` отработала, поэтому это код после `kill()`. 1 — код, который Python
  передаёт `TerminateProcess` (локально: `returncode after kill(): 1`). Если бы node сам
  завершился с 0 до kill, здесь был бы 0. Отсюда: node не завершился нормально; не подходит и
  сценарий «node закончил, а Python-сторона застряла». Оговорка: собственный `exit 1` node
  ровно к 30-й секунде этим не исключается, но тогда pipe закрылся бы раньше дедлайна.
- Job дошёл до конца и напечатал отчёт. Значит, повторный `communicate()` без таймаута
  вернулся: после смерти node других держателей write-концов stdout и stderr не было. С
  внуком-держателем он ждал бы выхода внука (прототип, 3.8). Сколько он длился, в логе нет.
- `endtime = 714.0`. В 3.12 на Windows `time.monotonic()` — это `GetTickCount64()`: локально
  `get_clock_info` даёт `implementation='GetTickCount64()'`, `resolution=0.015625`, значение
  совпало с uptime машины. Значит, `communicate` начался на 684,0 с после загрузки ОС.
- 607 символов скрипта меньше буфера анонимного pipe: локально 4 096 байт принимаются без
  чтения, дальше запись блокируется. Завершение записи не доказывает, что node читал stdin.

Чего лог не сохранил. Частичные stdout и stderr были в `exc.stdout` и `exc.stderr`, но
`TimeoutExpired.__str__` их не печатает, а pytest не показывает атрибуты. Неизвестны также
длительность `Popen()` (spawn), CPU и память node, его версия, другие процессы, точное время
вызова по часам.

Порядок вызовов. pytest собирает `tests/` по алфавиту; `pytest-xdist` и плагинов случайного
порядка в CI нет (`pyproject.toml`: `dev = ["pytest>=8"]`, `addopts` нет). Файлы, запускающие
Node, начинаются с индекса 130 из 646, и это `test_command_materials_compose.py`. Раньше
`node` встречается только как данные (`test_command_dsh_harness.py:324`, где это отвергаемый
ввод) или как Python-фейк (`tests/_fakedsh.py`). Продукт в коде Node не запускает, а
real-smoke тесты настоящих CLI без переменных `CONDUCT_*_EXECUTABLE` пропускаются. Упавший
тест (стр. 374) идёт в файле раньше второго (стр. 389), его первый параметр — ``docs/a`b.md``.
Номер этого элемента в сессии — около 4 067 из 17 859 (локально на HEAD индекс 4 066 из
17 915; до этого места между `04641ca` и HEAD менялись `test_adapter_boundary_launch.py` и
CAPPED в `test_command_line_cap.py`, отсюда ±2).

## 2. Гипотезы и чем их подтвердить или опровергнуть

Профили процесса, на которые ссылаются пункты, измерены в 3.6 и сведены в 5.3.

**H1. Холодный старт: первый запуск node.exe на свежей ВМ.** Статус: ведущая, не доказана.
- За: первый вызов Node в suite; 684 с после загрузки; оценка 0,07 % для «равномерной» модели.
- Против, частично: локально весь штраф первого запуска сидит в `CreateProcess`. Новый файл
  стоит 5,8–9,2 с, тот же файл по новому пути — 2,2 с, а время после spawn обычное, 46–55 мс
  (3.5). В 30 с может попасть только «холодная» часть внутри дочернего процесса: подкачка
  страниц образа (93 МБ) и чтение файлов с непрогретого диска.
- Чем проверить: поля «call #1», `spawn took`, `uptime` и профиль на дедлайне. Мало handles и
  памяти значит, что node не дошёл до bootstrap. Предупреждение о медленном, но прошедшем
  вызове покажет, бывает ли первый вызов на runner'ах регулярно дольше 2 с. Из уже
  существующих логов — раздел 4.

**H2. Антивирус (Defender).** Статус: возможен только как часть H1/H3. Включён ли Defender на
runner'е, по логу не видно.
- Проверка образа node.exe — в spawn (3.5), не в 30 с.
- Проверка открываемого JS-модуля: первое чтение `desk-wizard-materials.js` после checkout
  идёт внутри node и попадает в 30 с. Локально это +30 мс: медиана 82 мс против 49 мс, n=30.
  До 30 с это вырастет, только если занят сам MsMpEng (обновление сигнатур, сканирование
  после загрузки). Сам скрипт приходит через stdin и файлом не становится.
- Чем проверить: таблица процессов на дедлайне (MsMpEng.exe и другие фоновые процессы с
  памятью) и профиль «загрузился и ждёт». Окончательно — шаг CI `Get-MpComputerStatus`; это
  правка `ci.yml`, решение владельца, вне R1.6.

**H3. ESM-загрузка `file:///D:/...`.** Статус: не исключена.
- Node читает модуль и ищет `package.json` вверх по дереву D:. Остановка ввода-вывода на D:
  даст профиль «загрузился и ждёт» с пустым stdout.
- Против: остальные вызовы с тех же путей прошли; локально свежий файл стоит +30 мс.
- От H4 пассивно не отличить. Если первый же диагностированный случай даст этот профиль,
  следующий шаг — маркеры этапов внутри node (раздел 7).

**H4. Блокировка чтения stdin до EOF.** Статус: маловероятна.
- EOF был доступен: запись закончилась и write-конец закрыт (стр. 1630 достигнута).
  Write-конец stdin у Python не наследуемый: `CreatePipe(None, 0)`, наследуемым делается
  только конец ребёнка. Другого держателя быть не могло; остаётся сбой чтения в node/libuv.
- Локально около 4 800 вызовов без единого случая. Профиль тот же, что у H3.

**H5. Конкуренция с другими процессами за CPU и диск.** Статус: как единственная причина не
подтверждается.
- 8 процессов нагрузки CPU и 2 писателя на диск: медиана выросла в 2,3 раза (55 → 125–129
  мс), максимум 0,86 с — в 35 раз ниже 30 с. Восемь параллельных pytest: максимум 0,69 с.
- Вклад в H1–H3 возможен. Чем проверить: CPU node на дедлайне, число процессов и потоков.

**H6. Утечка унаследованных handle: pipe держит другой процесс.** Статус: как причина
таймаута №43 опровергнута.
- Тогда node завершился бы сам с 0, неудачный `TerminateProcess` дал бы `returncode` 0, а
  повторный `communicate()` ждал бы держателя. В логе 1 и завершённый job.
- Поле диагностики: `pipes closed in X s` против `pipes still open`.

**H7. Зависание в коде модуля на этом вводе.** Статус: опровергнута.
- Код детерминирован, циклы ограничены (`for (const char of text)`, без `while`). Тот же ввод
  прошёл в №42 (обе Windows), в №43 py3.11 и локально 1 000 раз в отдельном node (максимум
  0,64 с). Модуль, тест и helper не менялись между №42 и HEAD.
- Если на дедлайне CPU окажется близок к времени ожидания — пересмотреть.

**H8 (добавлена). node сделал работу, но не завершился.** Статус: не проверить. Признак — в
частичном stdout полный JSON. В №43 stdout потерян.

**H9 (добавлена). Пауза всей ВМ или остановка Python-стороны.** Остановка Python при
завершившемся node опровергнута кодом 1 (раздел 1). Пауза всей ВМ (обслуживание хоста)
пассивно от H3/H4 не отличима; признак — разрыв в отметках времени лога.

### 3.7 Проверки механизма

- После таймаута `run()` (timeout 2 с) частичный вывод сохраняется: `exc.stdout='partial\n'`
  для `console.log` перед вечным циклом, `exc.stdout='alive\n'` перед `setInterval`,
  `exc.stderr='to stderr\n'`. Перед `kill()` во всех трёх случаях `poll()` = `None`.
- Буфер stdin: ребёнок, не читающий stdin, принимает ровно 4 096 байт, дальше запись стоит.
- Запись stdin не входит в таймаут. Ребёнок начинает читать через 4 с, `timeout=1`: при 600
  и 4 096 символах `TimeoutExpired` через 1,01 с, при 10 000 — только через 4,03 с.
- pytest 9.1.1 печатает строки `exc.add_note(...)` строками `E` и в `--tb=short`, и в
  длинном виде.

### 3.8 Прототип диагностики (вне репозитория)

`proto/node_run_proto.py` — набросок helper'а из раздела 5, `proto/scenarios.py` — прогоны.

- Успешные вызовы (код 3 со stderr; JSON с `é`) дают тот же `(returncode, stdout, stderr)`,
  что `subprocess.run`.
- Настоящий node с `setInterval`, `timeout=2`: исключение через 2,50 с, заметки ниже (5.4).
- Держатель pipe. Внук с `detached: true` и унаследованными stdout/stderr живёт 20 с,
  `DRAIN_AFTER_KILL=1`: исключение через 2,50 с с заметкой `pipes still open`. Python-внук
  на 6 с, `DRAIN_AFTER_KILL=2`: с отцеплением pipe 3,84 с, без отцепления 6,1 с. Без
  отцепления выход из `with` закрывает объект pipe и ждёт поток-читатель до выхода держателя.
- Без `detached: true` внук node на Windows умирает вместе с родителем (по-видимому, libuv

### 5.1 Где

### 5.2 Контракт: вердикт и дедлайн как у `subprocess.run`

- Успешный путь равен `subprocess.run(argv, input=source, capture_output=True, text=True,
  encoding="utf-8", timeout=timeout, check=False)`: одна попытка, тот же `CompletedProcess`.
- Таймаут: тот же объект `subprocess.TimeoutExpired`, пойманный из первого `communicate`
  (`cmd`, `timeout` прежние), `stdout`/`stderr` — частичный вывод строкой, как у `run()` на
  Windows. Дополнительно — строки `exc.add_note(...)`: Python ≥ 3.11 (`requires-python`), pytest
  их печатает. Первая строка падения в логе не меняется.
- node получает ровно `timeout` секунд. Сбор фактов идёт после дедлайна и только на пути
  падения, ограничен: таблица процессов ≤ 5 с, сбор вывода после kill ≤ 10 с, проба версии ≤ 5
  с — не больше 20 с сверху.
- Никаких файлов, переменных окружения, повторов и новых зависимостей. Файлы в core-job'е
  бесполезны: у `test` в `ci.yml` нет `upload-artifact` (он есть только у `browser`, `wheel` и
  `wheel-road`), а шаг «The checkout is clean» требует чистого дерева. Поэтому всё — в текст.

### 5.3 Порядок на пути таймаута и поля

1. До kill — профиль процесса. Windows: `OpenProcess`, `GetExitCodeProcess`,
   `GetProcessTimes`, `K32GetProcessMemoryInfo`, `GetProcessHandleCount`. POSIX: `poll()` и
   строка процесса из `ps`.
2. До kill — таблица процессов. Windows: `tasklist /FO CSV /NH`; POSIX:
   `ps -A -o pid=,ppid=,stat=,time=,rss=,comm=`. В заметку: число процессов, живые процессы с
   тем же образом, фоновые процессы Windows из списка (раздел 6, п. 1).
3. `kill()`.
4. Сбор вывода с пределом и время закрытия pipe. Не закрылись — отцепить их от `Popen`.
5. Проба `<argv[0]> --version`: ответ и время. Ответ за десятки миллисекунд значит, что к
   этому моменту node на ВМ запускается нормально; если висит и проба, сбой шире одного
   процесса.
6. Заметки и `raise`.

Как читать профиль (калибровка — 3.6):

| Профиль на дедлайне | Чтение |
| --- | --- |
| handles < 20, рабочий набор < 10 МБ, CPU около 0 | не дошёл до bootstrap: H1, H2 |
| handles ≈ 170, ≈ 33 МБ, CPU ≈ 0,03 с, stdout пуст | загрузился и ждёт: H3, H4, H9 |
| CPU близок к времени ожидания | крутится в коде: H7 |
| в частичном stdout полный JSON | работа сделана, выход не состоялся: H8 |
| `pipes still open` после kill | pipe держит другой процесс: H6 |
| `spawn took` больше 1 с | дорогой `CreateProcess` (проверка образа) — вне 30 с |

Вывода о причине helper не пишет: только факты.
