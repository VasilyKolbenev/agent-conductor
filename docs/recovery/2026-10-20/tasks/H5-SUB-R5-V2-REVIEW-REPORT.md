## Решение

**Да: продолжать реализацию access-only без обратной записи для первого цикла Далио.**
Это утверждённое Codex техническое изменение пункта 4 TASK, а не смена продуктового объёма.
В relay не передаётся настоящий refresh token; из relay ничего не записывается в постоянный
login-home. `LOGIN_LOAN_OPEN` остаётся `False`; обязательные API-ключи и обход изоляции исключены.

Реализацию I2 можно продолжать по этому решению, исправляя C1–C4 ниже в соответствующих срезах.

До признания двух harness рабочими обязательны M2, проверки границы и настоящий цикл в UI.
**v2 без этих поправок не принят целиком; работоспособность живых подписок ещё не доказана.**

Причина выбора: возврат файла из недоверенной попытки создаёт путь подмены постоянного входа.
Отказ от copy-out убирает этот путь и гонку записи обновлённого refresh token. При этом access
token остаётся секретом: ребёнок видит его и имеет сеть; ограничение срока не устраняет риск утечки.

## Спека: обязательные поправки

### C1 — P1: Codex не читает предложенный файл без поля refresh_token

**Цитата:** DESIGN:118, «`strip`: `tokens` без `refresh_token`».
**Измерено:** установленный Codex 0.112.0, три синтетических случая, по одному запуску status.

| Случай | Exit | Наблюдаемый результат |
| --- | --- | --- |
| Полный fake refresh token | 0 | `Logged in using ChatGPT` |
| Поле `refresh_token` удалено, как в v2 | 1 | `missing field refresh_token` |
| Поле `refresh_token` — пустая строка | 0 | `Logged in using ChatGPT` |

Первый случай — контроль парсера с fake credentials, не разрешение передавать настоящий refresh.
Второй опровергает предложенный формат; третий подтверждает только разбор локального файла.
**Решение:** access-only означает отсутствие пригодного refresh-секрета, а не непременно ключа JSON.
Для Codex `refresh_token: ""` — допустимый кандидат для M2.
Не записывать его в настоящий login-home.
Claude проверяется отдельно: переносить на него форму Codex нельзя. Не подменять `last_refresh`
или срок токена ради прохождения проверки. Нужные account/id metadata берутся из исходного входа.

В `login --help` этой версии нет `--with-access-token`; добавлять его по современной документации
в pinned argv нельзя. Если минимальный вариант не работает, описать конкретную причину отказа.

### C2 — P1: claim должен следовать за успешным входом в boundary

**Цитаты:** DESIGN:145–146 ставит claim после copy-in «перед spawn», а :153–159 обещает отказ
на входе в `container_profile` как `NotStarted` до claim.
**По коду:** `adapters/harness_attempt.py:352–357,384–389`: `_spawn` сначала строит spec,
потом входит в `container_profile`, только внутри вызывает `runner.run`.

Если claim стоит перед `_spawn`, отказ создания контейнера оставит постоянный marker,
хотя квитанция заявит «не запускалось». Следующая попытка уже не сможет нормально повторить шаг.
**Решение:** для dispatch, planning/review и checker явный порядок:
`lease → copy-in → успешный enter boundary → claim → runner.run`.
Подготовка argv/spec и проверки готовности выполняются до claim. Сбой с неизвестным исходом
после claim сохраняет unknown; не снимать marker и не повторять возможную работу автоматически.
Тест через публичный transport: отказ enter, отсутствие marker, чистая lease, следующий допуск.

### C3 — P1: ожидаемые отказы подготовки не должны отравлять login lease

**Цитата:** DESIGN:147 называет отказы sweep/copy-in «типизированный `RelayRefused(code)`»;
§3.7 явно нормализует только вход и выход контейнера.
**По коду:** `src/conductor/ownership_login.py:249–255`: исключение из тела lease ставит
`lease.uncertain = True`. Обычная ошибка входного файла тогда может требовать recovery после reboot.

**Решение:** ожидаемые отказы подготовки возвращаются значением или перехватываются до выхода
из тела lease; публичная квитанция строится после чистого закрытия. Нельзя выпускать
`RelayRefused` через декоратор и нельзя безусловно очищать uncertain для любых исключений.
Настоящее недоказанное завершение дерева, `retire(False)` и потеря контроля сохраняют uncertain.
Тесты: sweep/copy-in/enter отказали до claim → marker отсутствует и следующая lease доступна;
потеря дерева → uncertain и отказ дальнейшего допуска остаются.

### C4 — P1: автоматический переход к copy-out не утверждён

**Цитаты:** DESIGN:25–26,242,246: при неудаче M2 «включается режим возврата», per-CLI `returns`.
Сам §7:253 называет подмену входа отдельным риском для решения владельца.
Такое переключение вернуло бы именно те полномочия, ради устранения которых выбран access-only.
**Решение:** §7 не входит в текущую реализацию и не является fallback. Если M2 не прошёл,
этот harness остаётся недоступным для задач; Opus передаёт конкретное препятствие Codex.
Copy-out, передача refresh token и расширение полномочий требуют отдельного решения.

## Доказательность и краткий путь к первому циклу

DESIGN:132 пишет «M3 подтверждает» refresh Claude, но :232–233 только планирует измерение;
`H5-SUB-R5-I1-REPORT.md:157–158` относит M1–M3 к непроверенному. Пока это гипотеза.
**Свежий токен достаточен для первого прохода:** перед каждым шагом, включая шаг после human gate
и checker, проверить оставшийся срок не меньше таймаута этой попытки плюс 10 минут.
Готовность не кешировать на весь цикл; в момент допуска токен всё ещё должен покрывать попытку.
JWT `exp` без проверки подписи используется только для времени, не как доказательство аккаунта.

При малом сроке — один подтверждённый штатный refresh вне boundary на отдельном login-home
продукта под lease либо отказ до claim с понятным действием повторного входа владельца.
Неподтверждённый refresh Claude не блокирует сценарий со свежим токеном. Не ждать его естественного
истечения ради старта; не открывать claim, если срок недостаточен или неизвестен.
Истёкший/отозванный токен во время работы — ошибка попытки без автоматического перезапуска.

Порядок для Opus:

1. Продолжить I2 с C1–C4; использовать I1 после его собственного ревью. Тестировать нужные
   публичные швы, отказ и успешный путь. Штатные protections/cleanup/redaction не ослаблять.
2. Подготовить владельцу входы в отдельные login-home. Выполнить M1 и по одному минимальному M2
   на CLI с фактическими argv, отфильтрованным env и relay-форматом; секреты не логировать.
   Успех на настоящем полном home не засчитывать за access-only. Проба вне AppContainer
   проверяет лишь совместимость auth; границу подтверждают native witness и запуск продукта.
3. Поставить wheel новой реализации, зафиксировать SHA/diff/hash; выполнить в UI все пять стадий
   `dalio-v5`: Claude планирует и делает, Codex проверяет точный результат, решения — владельцу.
   Не расширять проход до общего исследования остальных harness или повторного аудита R1–R4.

Бюджет сохранён: один цикл, до 6 task actions Claude и 2 checker Codex; это запуски harness,
не внутренние LLM/tool calls. M2 — не больше одного минимального запуска каждого CLI отдельно.
Негативный контроль из старого runbook и финальная приёмка не объявляются пройденными автоматически.
