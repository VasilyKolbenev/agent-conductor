# Почему браузерный Do не увидел результат в Windows

Исправление `135d87c` проверено локально. Приложение Windows заблокировало неподписанный тестовый двойник при первом вызове CLI. Исправленный браузерный тест запускает зарегистрированный двойник тем же закреплённым Python, что и tests/; выбор настоящего CLI не менялся. Задание `9cfb8d2`. Исходные файлы и результаты контролей собраны в `Documents/Codex/work/patch-fakeproc-evidence`.

## Два исходных случая

В обоих журналах лежат определение графа, инструкция, ограниченное разрешение, proposal, request и последнее событие `effect_lease`. После него нет `execution_observed`, результата действия, события успешного завершения или заключения проверяющего. Ни каталог временных файлов адаптера, ни журнал первого запуска CLI не появились. Windows-CodeIntegrity/Operational 3077 соответствует применению политики. Оба события каждого случая называют тот же файл, что находится в каталоге конкретного теста. Исходный Python-код ошибки из `Popen` в браузерном отчёте не сохранён.

Браузерный traceback заканчивается на ожидании `data-automation-state`: ожидались `waiting` и `complete`, а интерфейс оставался в `running` все 60 секунд разрешения. Сохранённый второй traceback проходит через `server.server_close → server_retirement.retire_resources → server_policy.release_server_owner → ProjectOwner.release → ProjectOwner.check` и заканчивается `OwnerRefused("recovery_required", "a process loan did not prove retirement")`. На пути запуска получить аренду нужно до создания процесса. `_procgroup.start` возвращает её с `retire(False)`, если создание завершилось исключением; `ProjectOwner` сохраняет неопределённое состояние. Этого механизма достаточно для объяснения наблюдений. Запись Windows связывает отказ с неподписанным файлом точнее, чем текст ошибки карточки.

Хеши сырых журналов и результатов тестов записаны в `incidents.json` и `extra-receipts.json`, номера событий и имена файлов — в `windows-integrity.json`. В подкаталогах `b6e2e0f` и `b4fbc0r` сохранены первоначальные stdout/stderr, failure, finish marker, records.jsonl, events.jsonl и активная запись аренды.

## Исправление и проверки

* Прежде штатная fixture была autouse только под `tests/conftest.py`. Pytest не применял её к соседней папке browser_tests. Общая fixture теперь подключена к исходному дереву тестов и к модулю браузерного Do. Подстановка действует только на Windows и только для точного зарегистрированного файла с совпадающим SHA-256. Изменённый файл отклоняется до Popen; незарегистрированные команды сохраняют обычный путь запуска.
* Новый отрицательный тест на исходной версии передавал повреждённый файл Windows и получал системный отказ. После исправления тот же тест получает отказ реестра по SHA-256 до запуска. Отдельная настоящая нативная проверка установленного Codex 0.164.0 прошла 1/1 с офлайн-подстановкой только на границе инференса.
* 140/140 связанных проверок владельца, двойников и Do прошли. Три браузерных учебных пути прошли отдельно, затем все 5/5 браузерных тестов Do в новом каталоге той же глубины, что в официальном порядке. Проверены фактические `count.py` и `test_count.py`, `checker` и одна записанная приёмка `offline-owner`. В интервале этой проверки отсутствуют 3033/3077, называющие файлы нового тестового каталога. Системная политика, продуктовый таймаут и требование доказать завершение процесса сохранены.

## Граница для настоящего запуска

Если пользовательский CLI не стартовал, готовый результат или успешный шаг не записывается. При аренде без подтверждённого завершения наблюдался устаревающий статус `running`, а закрытие владельца возвращало `recovery_required`. Отдельное улучшение интерфейса может отображать такой подтверждённый сервером отказ явно, показать идентификатор запуска и направить к предусмотренному восстановлению. Повтор задачи, запись успеха и освобождение аренды требуют собственных доказательств. Исправление затрагивает только тестовую среду.
