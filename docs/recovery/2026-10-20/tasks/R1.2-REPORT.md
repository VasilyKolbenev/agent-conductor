## Найдено, но не исправлено: R1.2b — слот навсегда занят после завершения плана при потерянном seed

Не относится к CI-сбою и этой правке (задание — только тесты, `policy_driver.py` в работе у другого
агента). Находка скептика 1. `PolicyDriver._tick` (`policy_driver.py:199-207`) сначала вызывает
`_seed_owed` → `seeds.settle` и при `seed_blocked` выходит, не доходя до `_select_next`, где
единственный `deactivate` для `complete` (`:258-260`). Если seed run'а потерян (папка
`work/_tasks/<task>/<item>` удалена, `CorruptSeed`, `StoreError`/`OSError`), а затем человек
принимает решение и план становится `complete`, слот остаётся `busy/plan_ended` навсегда:
automation показывает `complete/plan_ended`, pause/revoke завершённого run даёт 422, desk не
предлагает release для `busy`, очередь не качается, другой run получает `SlotBusy`, acceptance
считает run активным. Выход — перезапуск процесса или возврат папки. Нарушает контракт
`tests/test_policy_driver_queue.py:7-8`. Воспроизведение (вне репозитория):
`C:\Users\Пользователь\Documents\Codex\work\r12skeptic1\test_skeptic_slot_after_end.py`
(сценарий А: папка удалена у result gate, затем reject; сценарий Б: удаление внутри окна под
затвором; контроль). Непроверенная гипотеза второго триггера: `_next_node` →
`failure_sources` бросает на результате `unknown` (`policy_driver.py:306-307`) раньше проверки
`run_state` (`:308-310`). Нужна отдельная задача на продукт; новое свидетельство на неё не
влияет: затвор делегирует настоящему `seeds.settle`, seed целый.

## Правки после ревью Opus

Находка F1 (подтверждена): свидетельство окна не проверяло, что слот освобождает именно тик,
который разбудило решение. Драйвер может разбудить сам себя (`deactivate` и `activate` ставят
`_pending = True` и зовут `notify`, `policy_driver.py:113-121`), и тогда слот освобождает второй
тик, а не тот, что увидел решение. Мутант M6b проходил.

Правка только в `tests/test_command_flow_driver.py` (319 → 328 строк, самая длинная 99):

- `HeldTick.settle` считает в `seen` каждый тик, который нашёл решение в журнале, независимо от
  `armed` (раньше затвор смотрел на решение только вооружённым);
- после `run.until("the frame after the slot is freed", ...)` стоит `assert held.seen == 1` с
  сообщением «слот освобождает тик, разбуженный решением, а не тик, которым драйвер разбудил
  себя»;
- docstring теста и затвора говорят ровно проверяемое.

Выбор строгой формы. На зелёном пути второго тика до кадра не бывает: драйвер один поток, тик,
увидевший решение, освобождает слот в той же `_select_next`, `deactivate` ставит `_active = None`, и
следующий проход цикла, который будит `_pending`, идёт в `_pump_queue`, а не в `_tick`, то есть до
`settle` не доходит. Поэтому `== 1`, а не `>= 1`. Тик, начатый до решения, решения не видит и не
считается: он уже выставил `waiting` (после `settle`), когда `at_result_gate` вернулся.

Мутант M6b (на копии вне репозитория, правка исходника, не монкипатч): в `_select_next` при
`reason == "complete"` в первый раз для run ставится `_pending = True`, зовётся `notify()` и
возвращается `None, False` (слот не освобождён, кадра нет); освобождает слот и публикует кадр
второй, самобуждённый тик.

```diff
             if selected is None:

+                    owed = self.__dict__.setdefault("_m6b_woken", set())
+                    if run_id not in owed:
+                        owed.add(run_id)
+                        with self._condition:
+                            self._pending = True
+                            self._condition.notify()
```
