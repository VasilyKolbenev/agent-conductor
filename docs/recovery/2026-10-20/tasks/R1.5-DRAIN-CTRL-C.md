## 0. Вердикт

**Дефект продукта; тест прав, но вероятностен; у harness только диагностический недочёт.**

`conduct up` печатает URL и строку «Ctrl+C to stop» раньше, чем Ctrl+C начинает вести в drain.
`up_serve.py:73-74` печатает, затем `server_drain.py:108-110` создаёт и запускает поток
`conduct-http`, и только на `:111` начинается `try`, в котором `KeyboardInterrupt` превращается
в остановку. Ctrl+C в этом окне даёт непойманный `KeyboardInterrupt`. Python 3.8+ на POSIX
завершает такой процесс повторной посылкой себе SIGINT с `SIG_DFL`, отсюда `-2`; на Windows код
`0xC000013A`. Drain не идёт, `stopped` не пишется, голова владения остаётся `opened`. Следующий
`up` получает отказ `recovery_required`: «previous owner did not close; recover explicitly after
OS restart» (`ownership.py:115-116`).

Harness ждёт ровно то, что продукт объявляет готовностью: URL на stdout. Ничего раньше
готовности он не шлёт. Добавлять в harness отдельный маркер «готов к сигналу» нельзя: это спрятало
бы дефект продукта. Недочёт harness один: `assert child.wait_exit(WAIT) == 0` не показывает stderr
ребёнка. С ним лог CI сразу назвал бы строку `up_serve.py:73` и `KeyboardInterrupt`.

Человек в терминале в это окно практически не попадёт: окно меньше миллисекунды. Программная
остановка «прочитал URL — послал SIGINT» попадает: так делают обвязка, IDE и скрипты. Цена попадания
высокая — проект заперт до перезагрузки ОС и явного восстановления.

Минимальное исправление (A): объявлять URL изнутри охраняемой зоны, после старта
`conduct-http`. Детерминированный свидетель без `sleep` описан в разделе 8 и прототипирован.
Он краснеет на текущем коде и на мутанте порядка, зеленеет на A.

## 2. Почему именно -2: доказательство по коду

1. **`-2` — это непойманный `KeyboardInterrupt`, а не «Python не успел поставить обработчик».**
   С Python 3.8 (bpo-1054041) `Py_RunMain` после `Py_FinalizeEx` вызывает `exit_sigint()`, если
   верхний уровень завершился непойманным `KeyboardInterrupt`. На POSIX это
   `signal(SIGINT, SIG_DFL); kill(getpid(), SIGINT)`, и `Popen.returncode == -2`. На Windows
   возвращается `STATUS_CONTROL_C_EXIT` = `0xC000013A` = 3221225786. Python делает это
   намеренно, чтобы родитель видел «убит Ctrl+C».
2. **`SIG_DFL` в момент доставки исключён.** Сигнал послан только после того, как родитель прочитал
   URL. Значит, пройдены импорт пакета, `_install()` и весь `server.build`, а обработчик Python
   стоит с инициализации интерпретатора и ещё раз явно поставлен `set_console_ctrl_c("enabled")`.
   Продукт вызывает `signal.signal` только в `server_drain.py:87` и `:91-92`, и ставит там
   `notice.report`, прежний обработчик или `default_int_handler`, но никогда не `SIG_DFL`.
   `SIG_DFL` появляется лишь внутри `exit_sigint()`, то есть уже после непойманного исключения.
3. **Исключение возникает только в главном потоке.** Python-обработчики сигналов исполняются только
   там. Поток `conduct-http` и другие потоки `KeyboardInterrupt` не получают. `signal.signal` тоже
   вызывается только из главного потока (`server_drain.py:84`).
4. **Сигнал один.** `killpg` по группе, в которой один процесс; стандартные POSIX-сигналы не
   копятся. При `hub=False` у ребёнка нет наблюдателя stdin, а `serve_forever` сам не кончается.
   Значит, drain мог начаться только от этого же сигнала. Путь «drain → восстановление
   `default_int_handler` → поздний SIGINT на выходе» невозможен.
5. **Куда может уйти исключение.** После `up_serve.py:73` главный поток выполняет `:74` (печать
   в stderr), `server_drain.py:108-109` (`Thread(...)`) и `:110` (`http.start()`; внутри
   `_start_new_thread` и ожидание `self._started`). На POSIX блокирующий `acquire` прерывается
   сигналом: `EINTR` → `Py_MakePendingCalls` → `default_int_handler`. Исключение, поднятое в любой
   из этих точек, выходит из `serve_until_stopped` до `try`. Дальше оно проходит `serve` → `up` →
   `dispatch` → `main`, а `main` ловит только `store.StoreError` (`__main__.py:637-642`). Затем
   верхний уровень `_drain_child.py:216` и `exit_sigint()` → `-2`.

Вывод: `-2` в №41 означает, что SIGINT пришёл в окно `[запись URL в pipe … вход в try]`.

## 3. Окно: состав и ширина

Окно = остаток `print(URL, flush=True)` после `write`, печать в stderr, создание потока и
`http.start()`. Измерено на этой машине (Windows, 3.12, 16 запусков, отметки `perf_counter`
в ребёнке):

- от возврата `print(URL)` до возврата `http.start()`: 0,46–0,94 мс;
- от возврата `print(URL)` до первого `event.wait` внутри `try`: 0,60–1,18 мс.

Задержка родителя от записи URL до `seen` (URL замечен) — 1,2–15,7 мс: опрос раз в 20 мс плюс поток
чтения. На POSIX `killpg` идёт сразу после `seen`. Значит, сбой случается, когда родитель заметил URL
быстрее, чем ребёнок вошёл в `try`. Вероятность примерно W/20 мс. При W порядка 0,1–1 мс это доли
процента — единицы процентов на прогон. На Linux поток создаётся дешевле, поэтому W там, вероятно,
ближе к нижней границе (это оценка, не измерение). Под нагрузкой CI окно раздувается: GIL переходит
между потоками (`switchinterval` 5 мс), а ребёнок может быть вытеснен. Одиночный сбой в №41 и
зелёный Ubuntu 3.11 в №42 с этим согласуются. Привязки к 3.11 нет; macOS (POSIX) подвержен тому же.

## 5. Применим ли тест на Windows

Окно на Windows логически то же самое. CTRL_C_EVENT приходит в отдельный поток CRT и взводит флаг,
а главный поток поднимает `KeyboardInterrupt` на ближайшей проверке. Если она внутри `http.start()`,
исключение уходит наружу с `0xC000013A` (раздел 4.1). Но harness доставляет Ctrl+C через новый
процесс Python: одна его загрузка `python -I -c pass` занимает около 55 мс, плюс `AttachConsole` и
`GenerateConsoleCtrlEvent`. Сигнал приходит минимум через ~50 мс после `seen`, а окно около 1 мс.
Запас примерно в 50 раз: 12/12 естественных прогонов дали `0` и `closed`. Значит, на Windows этот
тест окно не ловит, но и ложно не краснеет. Детерминированный свидетель из раздела 8 работает
на всех ОС одинаково.

## 6. Ответ на вопрос «тест, продукт или оба»

- **Продукт — да.** Объявление готовности (URL и «Ctrl+C to stop») стоит раньше, чем Ctrl+C
  начинает вести в drain. После объявления одиночный Ctrl+C не должен давать грязного завершения.
  Дополнительно есть зазор для второго Ctrl+C (`server_drain.py:116-118`): после `except`, но до
  `notice.report`. Он шириной в микросекунды.
- **Тест и harness как синхронизация — нет.** Сигнал шлётся после объявленной продуктом
  готовности. Это правильная модель внешнего супервизора, и менять её не нужно.
- **Harness как диагностика — да, мелко.** Код выхода проверяется без stderr ребёнка. Так из лога
  CI потерялся traceback, который сразу назвал бы строку.
- **В реальной жизни:** человек в субмиллисекундное окно после URL практически не попадёт. Скрипт,
  IDE или обёртка, которые останавливают сервер сразу по URL, — попадут с вероятностью порядка
  процента. Последствие тяжёлое: traceback, `-2`/`0xC000013A`, нет `stopped`, голова `opened`,
  следующий `up` → `recovery_required` до перезагрузки ОС.

## 7. Исправление

### A. Минимальное (обязательно)

`serve_until_stopped` получает параметр `announce` и вызывает его первым оператором внутри `try`,
после `http.start()`. `up_serve.serve` переносит обе печати в `announce`. Поток стартует раньше
объявления, поэтому `shutdown()` после раннего Ctrl+C не повиснет. Объявление внутри `try`,
поэтому любой Ctrl+C, посланный после чтения URL, становится drain. Поведение stdout/stderr не
меняется: те же две строки, URL с `flush=True`, и печатаются они, пока сервер обслуживает.

Проверено на копии `fixA`: 190 passed (`test_server_drain_steps.py`, `test_cli.py`,
`test_up_status.py`, `test_operator_provider_config.py`, `test_server_drain.py` — все Ctrl+C-свидетели
на настоящей доставке Windows), 96 с.

### B. Усиление (по решению; отдельным коммитом)

Заменить `_absorbing_interrupts` на один обработчик на всё время ожидания и drain. Он поднимает
`KeyboardInterrupt` один раз и ставит свой флаг до `raise`. Дальше, а также если `stopper.event`
уже взведён, он только печатает уведомление. `Event.is_set()` читает флаг без блокировки, поэтому
вызывать его из обработчика безопасно. `Event.set()` из обработчика вызывать нельзя: может
случиться дедлок на `Condition` события. Если SIGINT был `SIG_IGN`, всё остаётся как есть. B
закрывает микросекундный зазор второго Ctrl+C. Проверено на копии `fixB`: 197 passed (те же
модули плюс `test_server_stopping_door.py`), 99 с.

### Шаг 1. Продукт (A)

`src/conductor/server_drain.py`, функция `serve_until_stopped`:

```python
def serve_until_stopped(srv, status, stopper: Stopper, *,
                        announce: Callable[[], object] = lambda: None,
                        clock: Callable[[], datetime] = _utcnow) -> int:
    """...
        announce: Says the server is ready (prints the URL). It runs after
            `conduct-http` has started and inside the region where Ctrl+C becomes
            the drain, so a Ctrl+C sent the moment the URL is read drains.
    ..."""
    http = threading.Thread(target=_serve_http, args=(srv, stopper), name="conduct-http",
                            daemon=True)
    http.start()
    try:
        announce()
        while not stopper.event.wait(WAIT_SLICE_SECONDS):
            ...
```

Порядок `http.start()` → `try:` → `announce()` обязателен: до старта потока `srv.shutdown()`

### Шаг 2. Детерминированный свидетель

В `tests/test_server_drain_steps.py` после

`from tests.test_store import good_lane, write_project`):

```python
_URL_LINE = re.compile(r"http://127\.0\.0\.1:\d+/\n")


class _ServingUntilShutdown:
    """Blocks in `serve_forever` until `shutdown`, and, like `socketserver.BaseServer`,
    cannot be shut down before its serve loop has run: a real one then waits forever."""

    server_address = ("127.0.0.1", 7777)

    def __init__(self) -> None:
        self.calls: list[str] = []
        self._ran, self._over = threading.Event(), threading.Event()

    def serve_forever(self) -> None:
        self.calls.append("serve_forever")
        self._ran.set()
        self._over.wait(30)

    def shutdown(self) -> None:
        assert self._ran.wait(5), "shutdown before the serve loop ran: a real server hangs here"
        self.calls.append("shutdown")
        self._over.set()

    def server_close(self) -> None:
        self.calls.append("server_close")


class _CtrlCWhenTheUrlIsOut(io.StringIO):
    """A stdout that delivers Ctrl+C right after the URL line has been flushed."""

    def __init__(self) -> None:
        super().__init__()
        self.fired = False

    def flush(self) -> None:
        super().flush()
        if not self.fired and _URL_LINE.search(self.getvalue()):
            self.fired = True
            signal.raise_signal(signal.SIGINT)     # what a parent that just read it sends


def test_a_ctrl_c_sent_the_moment_the_url_is_read_drains_and_never_escapes(
        tmp_path, monkeypatch, capsys):
    assert signal.getsignal(signal.SIGINT) is signal.default_int_handler, (
        "the witness needs Python's own Ctrl+C handler in place")
    fake = _ServingUntilShutdown()
    monkeypatch.setattr("conductor.server.build", lambda *args, **kwargs: fake)
    monkeypatch.setattr(server_drain, "enable_ctrl_c", lambda **kwargs: None)
    stdout = _CtrlCWhenTheUrlIsOut()
    monkeypatch.setattr(sys, "stdout", stdout)
    root = write_project(tmp_path, lanes={"claude": good_lane()})
    try:
        code = main(["up", "--dir", str(root), "--port", "0"])
    except KeyboardInterrupt:
        pytest.fail("a Ctrl+C sent once the URL was out escaped the drain: the process would "
                    "die of SIGINT (-2 / 0xC000013A) with its owner still opened")
    assert stdout.fired, "the URL line never reached stdout"
    assert code == 0, capsys.readouterr().err
    assert fake.calls == ["serve_forever", "shutdown", "server_close"]
    assert signal.getsignal(signal.SIGINT) is signal.default_int_handler
```

Ловить `KeyboardInterrupt` в тесте обязательно: иначе pytest примет его за Ctrl+C пользователя и
оборвёт сессию. Ни `sleep`, ни таймингов: сигнал рождается внутри `flush` строки URL, то есть в
самый ранний момент, когда родитель может её прочитать. Ограниченное ожидание `_ran.wait(5)` —
не тайминг, а граница дедлока; на верном коде оно возвращается сразу.
