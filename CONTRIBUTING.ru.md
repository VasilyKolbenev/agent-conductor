# Участие в разработке December Command

[English](CONTRIBUTING.md) · [README](README.ru.md) · [Документация](docs/index.ru.md) · [Архитектура](docs/architecture.ru.md)

Можно помочь более понятным текстом, воспроизводимым сообщением об ошибке, небольшим исправлением или новой возможностью. Сначала разбираться во всём проекте не нужно. Опишите, что человек должен суметь сделать, и найдите минимальное связное изменение, которое это обеспечит.

## Подготовьте рабочую копию

Нужны Git и Python 3.11 или новее. Создайте форк репозитория на GitHub, если вам нужно место для отправки изменений, затем клонируйте его и перейдите в корень. Используйте ветку или коммит, согласованные для задачи: основная ветка сама по себе не подтверждает, что перед вами проверенный кандидат выпуска.

Создайте виртуальное окружение, чтобы зависимости проекта находились вместе. Команды ниже обращаются к его исполняемым файлам напрямую, поэтому активировать окружение необязательно.

Windows PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev,browser]"
.\.venv\Scripts\conduct.exe demo
```

macOS / Linux:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[dev,browser]"
.venv/bin/conduct demo
```

Откройте адрес, который напечатает `conduct demo`; остановить сервер можно через `Ctrl+C`. Демо использует готовые данные из комплекта во временном каталоге и не делает платных вызовов моделей. Для демо и обычных тестов не нужны вход в аккаунт поставщика или API-ключ. Настройка настоящего проекта описана отдельно в [руководстве первого запуска](docs/first-run-v1.md).

Редактируемая установка подхватывает изменения исходников без переустановки. Установите оба extra: `dev` добавляет pytest, а `browser` — также Playwright и Pillow. Даже набор `tests/` импортирует Playwright через `tests/test_browser_gate.py` → `browser_tests/conftest.py`. Сам Chromium нужен для запуска браузерных проверок, а не просто для сбора этого набора. Команды для macOS не означают, что конкретный выпуск проверен на macOS; выполненные проверки платформ перечислены в руководстве первого запуска.

## Найдите нужную часть проекта

Начните с [обзора архитектуры](docs/architecture.ru.md), затем читайте соседние исходники и тесты вместе.

- `src/conductor/schema.py`, `store.py`, `merge.py` и `report.py` отвечают за данные линий агентов и вычисляемый отчёт о проекте.
- `src/conductor/command/` содержит процессы, запуски, выполнение и адаптеры поставщиков.
- `src/conductor/panel/` содержит браузерный интерфейс, включая Workflow Studio.
- `tests/` проверяет поведение Python и контракты исходников; `browser_tests/` — отрисованное приложение в Chromium.

Сохраняйте существующие границы. В Studio файл `studio-model.js` преобразует данные без обращения к DOM или сети; за обмен с сервером отвечает `studio.js`. Допустимые импорты и ограничения размера файлов проверяются в [test_studio_source.py](tests/test_studio_source.py). Циклы импортов адаптеров и их публичные интерфейсы проверяются в [test_adapter_module_graph.py](tests/test_adapter_module_graph.py). Перед разделением или переносом модуля прочитайте соответствующую проверку.

Интерфейс должен получать возможности поставщиков из контракта серверной части, а не придумывать собственный жёстко заданный список. Успешное завершение дочернего процесса ещё не доказывает, что его работа проверена. Сохраняйте эти различия в поведении, подписях и документации.

## Проверьте своё изменение

Для обычного вклада выбирайте тесты, которые проверяют затронутое поведение. Например, изменение готового демо линий агентов связано с `tests/test_demo.py`: он проверяет схему данных, блокирующие проблемы, разногласие и очередь решений человека.

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_demo.py
```

macOS / Linux:

```sh
.venv/bin/python -m pytest -q tests/test_demo.py
```

Замените этот путь на подходящий файл или идентификатор теста pytest для своей задачи. Для изменений интерфейса осмотрите затронутый экран и выберите соответствующие проверки `browser_tests/test_*.py`: проверки исходников не подтверждают отрисовку. Перед их запуском установите Chromium через Python из виртуального окружения с аргументами `-m playwright install chromium`. На Linux также могут понадобиться системные зависимости Playwright (`-m playwright install --with-deps chromium`).

Полный набор нужен в CI, при подготовке выпуска или когда масштаб изменения этого требует. Из корня репозитория:

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m playwright install chromium
.\.venv\Scripts\python.exe browser_tests/gate.py
.\.venv\Scripts\python.exe browser_tests/gate.py --reverse
```

macOS / Linux:

```sh
.venv/bin/python -m pytest -q
.venv/bin/python -m playwright install chromium
.venv/bin/python browser_tests/gate.py
.venv/bin/python browser_tests/gate.py --reverse
```

Обычная команда pytest собирает `tests/`. Браузерный gate запускает каждый браузерный модуль в отдельном процессе и сохраняет свидетельства во временный каталог; для выпуска важны прямой и обратный порядок. Обычный `pytest browser_tests` не заменяет выпускной gate. Остальные проверки, включая помощник `scripts/mutate_merge.py`, описаны в [конфигурации CI](.github/workflows/ci.yml) и [руководстве проверки выпуска](docs/release-smoke.md). Читайте ошибки и число собранных тестов; не выдавайте невыполненную проверку или успешный код завершения процесса за подтверждённое поведение.

## Работайте с AI-помощником

Дайте помощнику конкретный результат, область для изучения и границы изменения. Проверяйте его diff так же, как любой другой вклад.

- Попросите изучить затронутый код, контракты и тесты, затем объяснить ожидаемое поведение до редактирования.
- Сохраняйте существующие правки пользователя. Избегайте полной перезаписи файлов, посторонней уборки, ослабления или удаления проверок только ради успешного прогона.
- Если поведение меняет спецификацию, согласуйте настоящую реализацию, нужные проверки и документацию. Одна правка спецификации не реализует возможность.
- Не помещайте API-ключи и токены в чат, файлы репозитория, снимки экрана и логи. Для явно разрешённой задачи с настоящим поставщиком используйте описанную настройку переменных окружения.
- Запросите точные команды проверок, результаты и перечень непроверенного. Для обычной разработки используйте готовые тестовые данные и подставных поставщиков.

Скопируйте и адаптируйте это задание:

```text
Цель: [наблюдаемое поведение для пользователя и конкретный пример].
Сначала изучи: [нужные файлы] и соседние контракты/тесты.
Объём: минимальное связное изменение; сохрани существующие правки пользователя.
Объясни ожидаемое поведение, затем реализуй его без ослабления проверок.
Используй тестовые данные; не вызывай настоящих поставщиков и не работай с ключами.
Проверь через [нужный файл/идентификатор теста] и укажи, что осталось непроверенным.
```

## Отправьте первый pull request

1. Выберите одну проблему и опишите текущее и ожидаемое поведение. Крупную возможность сначала обсудите в issue.
2. Создайте ветку в своей копии. Внесите небольшое законченное изменение и синхронизируйте английскую и русскую версии парной документации.
3. Запустите нужные проверки, прочитайте `git diff` и `git status`, добавьте в индекс только нужные файлы. Не включайте сгенерированные результаты и секреты в коммит.
4. Сделайте коммит с понятным описанием, отправьте ветку в свой форк и откройте pull request. Укажите проблему, итоговое поведение, действительно выполненные проверки и оставшиеся ограничения. Для раннего обсуждения подходит черновой PR.

Если застряли, приложите команду, операционную систему, версию Python и минимальный пример без личных данных. Точный вопрос или воспроизводимое описание проблемы — уже полезный вклад.
